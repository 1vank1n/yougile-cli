# 0007. Публикация в PyPI — отдельный job, а не шаг в `release`

## Контекст

Релизный workflow уже одним job'ом собирает пакет, сверяет версию с тегом, гоняет линтер, типы и тесты. Публикация через Trusted Publishing требует `permissions: id-token: write` на GitHub Actions.

## Решение

Публикация — отдельный job `publish` в `release.yml`, с единственным правом `id-token: write` и единственным шагом — вызовом `pypa/gh-action-pypi-publish`. Job запускается после успешного релизного job'а через `needs:`.

## Почему

Отвергнут вариант добавить публикацию шагом в существующий job сборки/тестов/релиза: права в GitHub Actions выдаются на job целиком, поэтому такой шаг открыл бы OIDC-токен любому другому шагу того же job'а — включая сторонние actions для сборки, линтинга и тестов. Это расширяет поверхность атаки без необходимости: скомпрометированный шаг линтера получил бы доступ к тому же токену, что и публикация на PyPI.

Отдельный job с одним правом и одним шагом минимизирует то, что вообще может увидеть OIDC-токен.

## Последствия

Между job'ами нужны явный `needs` и передача артефакта сборки (см. 0009) — job'ы больше не изолированы друг от друга по данным, только по правам. Разделение платит временем: раннер для `publish` поднимается заново, а не переиспользует уже прогретое окружение релизного job'а.

Слияние публикации обратно в один job в будущем — не правка, а пересмотр модели прав: придётся заново решать, какие шаги вправе видеть OIDC-токен, и заново отделять периметр, который сейчас закрыт самим фактом job'а с единственным шагом.
