# 0008. Аутентификация на PyPI — Trusted Publishing, а не токен в секретах

## Контекст

PyPI поддерживает публикацию из CI двумя способами: API-токен в секретах репозитория или Trusted Publishing — обмен OIDC-токена GitHub Actions на короткоживущий токен PyPI. Токен в секретах — стандартный путь, который при проектировании публикации приходится сознательно отклонять, а не просто не заметить.

## Решение

Публикующий job аутентифицируется через Trusted Publishing: `pypa/gh-action-pypi-publish` обменивает OIDC-токен job'а (`id-token: write`) на токен PyPI. Секретов в репозитории нет.

## Почему

Отвергнут долгоживущий API-токен PyPI в GitHub Secrets: его нужно завести вручную на pypi.org, положить в секреты репозитория, ротировать при подозрении на утечку и вручную сужать область действия — по умолчанию токен PyPI выдаётся на весь аккаунт, а не на один проект. Каждый из этих шагов — источник расхождения между тем, что настроено, и тем, что должно быть настроено.

Trusted Publishing снимает этот класс проблем: токен короткоживущий, выпускается только для конкретного workflow конкретного репозитория и нигде не хранится между запусками — нечему утечь и нечего ротировать.

## Последствия

Первая публикация не заработает сама по себе: на pypi.org нужно один раз вручную завести pending publisher с именем владельца, репозитория и файла workflow — это действие вне кода, кодом не закрывается.

Если имя workflow-файла или репозиторий сменятся, синхронно нужно поправить и настройку publisher на PyPI — иначе обмен токена откажет прямо на релизе, и узнают об этом постфактум.

Откат к токену в секретах — не правка одного файла: помимо добавления секрета в репозиторий, на PyPI нужно вручную завести токен и отдельно отозвать pending publisher, то есть менять конфигурацию на стороне, которую сам репозиторий не контролирует.
